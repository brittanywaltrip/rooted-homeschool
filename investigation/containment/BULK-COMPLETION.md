# Protected bulk completion compatibility

`commit_scheduler_bulk_completion` is a fixed operation for one goal, at most 100 unique unfinished/unskipped selected rows. It takes the exact goal/rows/vacations snapshot, family completion payloads, and the observed local day. It locks the goal and rows, profile and calendar, checks the day again, applies completions, and calls `scheduler_respread_locked` in the same transaction. Work/content and row membership cannot change. Each selected update checks its row count and exact resulting payload, including a trigger that silently suppresses an update.

The existing private action receipt stores only scheduling beforefields plus the prior goal pointer/completion timestamp and a SHA-256 full afterstate hash. `undo_scheduler_action` restores the entire recorded scheduling state, highest queue slot first, only while the full state is unchanged. It does not invoke reopen/make-up semantics or run a fresh tail projection. Later notes or work make Undo stale. Existing 10-minute expiry, scrubbing and pause behavior apply through the shared receipt/Undo contract.

Plan runs one protected transaction per goal; different goals are independently atomic. Legacy rows retain the old completion writer, serialized within a goal. Its explicit legacy fallback does not silently upgrade to individual protected operations if activation races the batch: the database guard refuses instead. Protected groups do not receive an additional tail re-spread that would invalidate their receipt. Confirmed successes, refusals and unknown outcomes have separate counts. A “Check result” action retries only the unresolved original request with the same ID and preimage, even after reload shows completed rows. Busy after an unknown result cannot discard that original request. Normal Plan completion also resolves its pending receipt before interpreting a checked row as an uncomplete request; a follow-up re-spread failure is reported as a saved completion with incomplete schedule refresh.

Local evidence: `bulk-completion-postgrest.py ../synthetic-runtime` uses a new disposable synthetic owner and loopback-only Colima, removes every owned row and receipt, and checks no global fixture baseline while other disjoint tests run. `bulk-completion-results.json` records the executed cases. The TypeScript bridge deliberately loses two actual committed responses, replays the exact request, then exercises receipt Undo. Unit tests cover unknown/busy retention, different selection refusal, stale local day, explicit SQL failure, missing protected endpoint and grouped legacy serialization.

Limits: batches over 100 selected lessons in one goal refuse before writes; no automatic splitting that would weaken exact Undo. This is not whole-family atomicity. Browser end-to-end confirmation is owned by the parent task. Hosted deployment, cohort activation and real family changes remain separate approvals.
